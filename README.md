## Открыть приложение

Пробная версия: https://anevidina-bot.github.io/100-days-challenge/ . Она работает на GitHub Pages с хранением записей и фото только в браузере. Email-входа, серверного восстановления и переноса между устройствами в этой версии нет. Для отдельной копии истории используйте JSON-экспорт. Полноценная серверная версия и её инструкции остаются ниже.

## Простой пробный запуск

Для проверки первого запуска без настройки почты: `node scripts/try-locally.mjs`, затем откройте http://localhost:8788 и нажмите «Начать проверку». Данные сохраняются в отдельном каталоге `data-local-trial` на компьютере. Это локальный личный режим; email, перенос на телефон и внешние push не подключены. Он не содержит вымышленных исходных данных. Для сброса используйте удаление аккаунта в настройках; следующий вход начнётся с пустого профиля. Обычный производственный запуск не разрешает этот режим.

# 100 дней · ваш ритм

Русскоязычная мобильная PWA для личного дневника привычек. Пакет подготовлен для отдельного хостинга с входом по email-коду, как вы выбрали. Серверная версия не развёрнута. Для проверки доступна отдельная браузерная версия на GitHub Pages.

**Статус: версия 0.4 для проверки и подготовки развёртывания. Полная приёмка внешних функций ещё не завершена.** Реализованы два числовых сценария питания: под целевой вес к выбранной дате и настраиваемый дефицит 0–25% (по умолчанию 15%). Динамическая модель Hall/NIDDK и обратный подбор численно сверены с официальной реализацией. Подробности, допущения и пределы проверки — `MODEL_VALIDATION.md`.

## Что уже работает

- Вход по одноразовому email-коду; хеширование кодов, срок 10 минут, лимиты попыток и повторных отправок. Реальная отправка предусмотрена через Resend и требует настройки.
- Серверная SQLite-база: отдельные профили, версии целей, челленджи, дни, история правок, расписания и переносы тренировок, результаты тренировок, замеры, награды, фотографии, настройки и операции синхронизации. Все API проверяют владельца.
- Первый запуск, ручной дневник, накопление привычек, все 10 этапов, подтверждение целей воды/шагов и выбора тренировочных дней при открытии новых этапов.
- Калории ±100 включительно, белок, правило продуктов с добавленным сахаром, вода, заменяемые цели шагов, баланс БЖУ с одним полем белка.
- Закрытие дня по сохранённому часовому поясу; переход этапа на следующий день, необязательная последовательность успешных дней, остановка после сотого успешного дня.
- Календарь, редактирование прошлых показателей с журналом правок и сохранением начисленного прогресса; запрет изменения прошлых тренировок.
- Переносы тренировок в пределах недели, пауза/возобновление со следующего дня, будущий старт, новый запуск с архивом и сохранением наград.
- Вес и отдельные графики замеров, сравнение двух фотографий, предложение пересчёта после −5 кг от принятого расчёта. Фото выдаются только владельцу и не лежат в публичной папке.
- Автономный кеш интерфейса и дневника, очередь изменений в IndexedDB, идемпотентная синхронизация, явный выбор при конфликте с другим устройством. Повторная попытка каждые 30 секунд при открытом приложении, при восстановлении сети и вручную.
- JSON с историей и нормами, CSV показателей/замеров, TAR-архив реальных фото; удаление аккаунта и фотографий.
- Серверный планировщик push с защитой от повторов, утренними/вечерними настройками, фильтром незаполненных задач и исключением дней паузы. Нужны библиотека web-push, VAPID-ключи и разрешение браузера.
- Резервное копирование согласованного снимка SQLite и связанных фото, проверка целостности и восстановление в новый каталог.

## Быстрая локальная проверка на Windows

Нужен установленный Node.js **24 или новее**. Базовые функции используют только стандартные модули Node; npm-пакеты для дневника не нужны.

1. Распакуйте архив в отдельную папку.
2. Скопируйте `.env.example` в `.env`.
3. Для просмотра страницы входа достаточно запустить `Запуск.cmd` и открыть `http://localhost:8787`. Без почтовых настроек страница честно покажет, что отправка кодов недоступна.
4. Чтобы войти и вести реальный дневник, настройте почту по следующему разделу и перезапустите сервер.

Альтернатива через PowerShell из папки приложения:

```powershell
Copy-Item .env.example .env
node --env-file=.env src/server.mjs
```

Остановка — Ctrl+C в окне сервера. Рабочие записи появляются в `data/challenge.sqlite`, фотографии — в `data/photos`. Не удаляйте `data`, если хотите сохранить историю. Локальный HTTP-адрес подходит только для этого компьютера. Чтобы установить PWA и пользоваться ей на телефоне, нужен доступный телефону HTTPS-сервер.

## Настройка реального email-входа

В `.env` задайте:

```dotenv
RESEND_API_KEY=ваш_секретный_API_ключ
EMAIL_FROM=100 дней <вход@ваш-подтверждённый-домен>
AUTH_SECRET=случайная_строка_длиной_не_менее_32_символов
```

У отправителя должен быть подтверждён домен в Resend. [Официальный API отправки](https://resend.com/docs/api-reference/emails/send-email). Регистрация сервиса и DNS-настройка не выполнены в этой сессии. Доступность сервиса и его тариф проверяются при выборе хостинга; приложение само не содержит оплаты или рекламы, но инфраструктура может иметь собственную стоимость.

Генерация секрета на своём компьютере:

```powershell
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"
```

Для первоначального личного использования добавьте `ALLOWED_EMAILS=ваш@email`. Пустое значение разрешает регистрацию любого email. Разрешённые пользователи всё равно имеют отдельные данные. Коды никогда не возвращаются API и не печатаются в журналы. Обычный сервер требует email-вход. Отдельный пробный режим включается только специальным локальным запуском и запрещён в production.

## Размещение на HTTPS-сервере

В комплекте `Dockerfile`, `compose.yaml` и пример `Caddyfile.example`. Рекомендуемый сценарий — один постоянно работающий экземпляр приложения на сервере с постоянным диском; одноразовые/эфемерные файловые системы не подходят для SQLite и фотографий.

1. Подготовьте сервер с Docker Compose и домен, направленный на этот сервер.
2. Перенесите исходники, создайте `.env`, настройте почту и `AUTH_SECRET`.
3. Поменяйте `APP_ORIGIN` на точный HTTPS-адрес, например `https://challenge.example.com`, и установите `COOKIE_SECURE=true`. Без завершающего `/`.
4. На Linux создайте каталоги и дайте контейнерному пользователю UID 1000 право записи:

```sh
mkdir -p data backups
sudo chown 1000:1000 data backups
docker compose up -d --build
```

5. Установите Caddy как обратный прокси и замените пример домена в `Caddyfile.example` на свой. Порт 8787 в compose доступен только через loopback хоста. Прокси должен завершать TLS и перенаправлять на него запросы. Наружу открываются только необходимые порты прокси, а не SQLite/папки данных.
6. Откройте HTTPS-адрес, запросите настоящий код, войдите, заполните профиль и сохраните запись. Повторите вход на другом устройстве и проверьте историю/фото.

Docker-образ и HTTPS-доставка в этой сессии **не запускались**. В режиме production сервер откажется запускаться без HTTPS-origin, secure cookie и почтовых настроек. `.env` нельзя публиковать, отправлять в Git или класть в публичный каталог. Диск и резервные копии должны быть доступны только администратору, желательно с шифрованием на уровне хостинга. Журналы прокси не должны собирать тела запросов, cookie, коды или фотографии.

После запуска откройте адрес в браузере HONOR → меню → «Установить приложение» / «На главный экран». Веб-манифест, service worker и PNG-иконки 192/512 включены. Установка и фактическая работа на HONOR 200 Pro / Android 16 ещё требуют проверки на вашем телефоне.

## Уведомления

В Docker зависимость `web-push@3.6.7` устанавливается при сборке. Для запуска без Docker установите её отдельно:

```sh
npm install --no-save web-push@3.6.7
node --input-type=module -e "import webpush from 'web-push'; console.log(webpush.generateVAPIDKeys())"
```

Сохраните пару в `.env` как `VAPID_PUBLIC_KEY` и `VAPID_PRIVATE_KEY`; `VAPID_SUBJECT` — ваш контакт `mailto:...`. Перезапустите сервер, затем в настройках приложения нажмите разрешение уведомлений. Секретный ключ остаётся на сервере. [Документация библиотеки](https://github.com/web-push-libs/web-push).

Сервер проверяет события каждые 30 секунд и отправляет только в течение 15 минут после выбранного времени. Если сервер был выключен всё это окно, устаревшее напоминание не отправляется. Отправка каждой комбинации пользователь/дата/тип резервируется один раз; неудачная попытка не вызывает повторного события. Android/браузер/сеть могут задержать доставку. Для работы при закрытой PWA сам сервер должен продолжать работать. Боевая доставка push пока не проверена, и без ключей интерфейс показывает «не настроено».

## Офлайн и границы суток

Первый вход, первая загрузка оболочки, фотографии, экспорт и удаление аккаунта требуют сети. После этого текстовые показатели и замеры доступны из кеша и попадают в очередь. До ответа сервера показывается «Ожидает синхронизации», а не «Сохранено». Кеш принадлежит аккаунту на этом устройстве и удаляется при выходе; используйте личный профиль браузера.

Конфликт не перезаписывает серверные данные молча: приложение показывает своё изменение и серверные значения. Можно применить ввод или оставить серверную версию. Запрос с тем же ID операции не создаёт второй экземпляр записи.

**Ограничение 0.1:** если офлайн-запись дошла до сервера уже после закрытия дня, она сохраняется только после явного согласия как исправление истории. Процент обновляется, ранее начисленный прогресс не перестраивается. Прошедшую тренировку отметить или перенести нельзя. Это следствие замороженного прогресса и серверного закрытия дней; автоматическое начисление за запоздавшие офлайн-события не реализовано. Длинный офлайн-период поэтому может задерживать продвижение по этапам.

При переводе часового пояса назад уже закрытая календарная дата не открывается второй раз. При переводе вперёд новый день появляется после закрытия предыдущего по его сохранённому моменту окончания. Смена зоны не изменяет старые записи. Если страница оставалась открыта во время полуночи, обновите её для нового дневного экрана; редактирование старого дня проходит через предупреждение об истории.

## Копии, восстановление и удаление

Создать копию вручную:

```sh
node --env-file=.env scripts/backup.mjs
# либо в развёрнутом контейнере:
docker compose exec -T app node scripts/backup.mjs
```

По умолчанию копии — `backups/backup-...`, рабочие данные — `data/`. Каталоги должны различаться. SQLite копируется средствами online backup API, затем копируются только фото, перечисленные в снимке. При отсутствующем фото копия считается неудачной. Сессии и действующие коды из копии удаляются. Ротация удаляет корректно распознанные копии старше 30 дней **при выполнении скрипта**.

Для ежедневной автоматизации на сервере настройте cron, например (пути замените своими):

```cron
0 3 * * * cd /opt/100days && docker compose exec -T app node scripts/backup.mjs
```

Планировщик ещё не установлен. Скопируйте резервные копии в защищённое отдельное хранилище с той же максимальной длительностью 30 дней и контролируйте успешность заданий. Без этого отказ одного диска уничтожит и базу, и локальные копии. Политика удаления из резервных копий действует только при настроенной ротации также на всех внешних копиях/снимках провайдера.

Восстановление выполняйте при остановленном сервере в **новый пустой каталог**, не поверх рабочей базы:

```sh
node scripts/restore.mjs backups/backup-ИМЯ data-restored
```

Скрипт проверяет SQLite integrity/foreign keys, манифест и наличие всех фотографий, затем переносит снимок. После этого укажите новый каталог как `DATA_DIR` или замените подключаемый том и выполните новый вход по email. Перед переходом на восстановленную старую копию учтите удаления аккаунтов после её даты: нельзя возвращать уже удалённые аккаунты в действующую систему без повторного удаления.

Удаление аккаунта в приложении удаляет его записи и фото с рабочего сервера и завершает сессии. Из существующих защищённых копий они исчезают при истечении срока ротации, не позднее 30 дней при правильно настроенной инфраструктуре. Скрипт восстановления был проверен на тестовой базе с настоящим файлом фото, а не только на пустой схеме.

## Проверки и оставшаяся приёмка

```sh
node --test tests/*.test.mjs
```

Тесты создают отдельные временные базы с вымышленными данными, не используют ваш почтовый ящик и не посылают письма. Тестовый HTTP-сервер использует порт 18787; порт должен быть свободен. Проверяются правила этапов и границы, обе DST-границы суток, тренировки, изоляция аккаунтов, сессии, повтор запросов, конфликты, CSV/JSON/TAR, фото, удаление и восстановление копии. Итог последнего запуска — `TEST_RESULTS.txt`. В браузере отдельно проверены мобильный главный экран, календарь, графики и сохранение/перезагрузка/синхронизация при остановке сервера.

До ежедневного использования остаются: размещение с HTTPS и постоянным диском, реальное письмо на ваш email, проверка телефона и установки, доставка push, активная ротация внешних копий. Числовая модель проверена на вымышленных эталонных профилях; индивидуальная точность прогноза не гарантируется. Реальные интеграции отсутствуют; результаты исследования — `INTEGRATIONS.md`. Нельзя считать прохождение локальных тестов подтверждением этих внешних возможностей.

## Файлы проекта

- `src/domain.mjs` — расчёты, снимки норм, задачи, этапы, календарные правила.
- `src/store.mjs` — SQLite и транзакции; `src/server.mjs` — HTTP, email-вход, закрытые фото, синхронизация, экспорт, push.
- `public/` — интерфейс без сборки, стили, service worker и PWA-манифест.
- `scripts/` — копирование и восстановление; `tests/` — проверки.
- `CALCULATION_RULES.md` — таблица с источниками и изменениями v0.2/v0.3 по запросам пользователя; `INTEGRATIONS.md` — проверка официальной документации.

Версия схемы SQLite: 1. Для следующих выпусков изменения схемы должны оформляться явными миграциями; не меняйте существующую рабочую базу вручную.

Изменение расчётных правил v0.2: ИМТ ниже 25 больше не отключает умеренный дефицит. При текущем/целевом ИМТ ниже 18,5 и других ограничениях автоматический дефицит недоступен. Умеренный сценарий составляет 15% от поддержания с прежними пределами. В v0.3 рядом добавлен независимый динамический расчёт под вес к дате.

## Два значения на экране

В первом запуске и «Настройки → Два варианта калорийности» укажите желаемый вес и дату. Приложение сразу сравнит вариант к сроку и умеренный вариант. У каждого показаны ккал, дефицит, процент и модельный вес к дате. Недопустимый вариант не выбирается; можно изменить срок/вес. Для сохранения выберите доступную карточку и нажмите «Применить выбранный вариант». Новые нормы действуют со следующего дня. При смене даты расчёт обновляется; цель за 100 успешных дней и календарный срок прогноза различаются. В ранних сохранённых версиях целей числового прогноза может не быть; он появляется у новой принятой версии, не дописывается в прошлую историю.

## Настройка процента и срока (v0.4)

Откройте «Настройки» → «Два варианта калорийности». Задайте вес и дату; двигайте ползунок процента, чтобы сравнить калории и модельный вес. Выберите карточку «К целевому весу к дате» или «По проценту дефицита» и нажмите «Применить выбранный вариант». При недоступном сроке кнопка «Использовать эту дату» подставит модельную дату с допустимым дефицитом; затем выберите карточку к дате. Новая цель действует со следующего дня. Процент доступен также при первом входе.
